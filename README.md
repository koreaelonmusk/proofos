# ProofOS

**Evidence-first autonomous agents that prove their work before claiming completion.**

Google All Things Agentic Hackathon 2026  
Target track: **Fortified Enterprise Fleet**

## Core invariant

> A completion claim is never accepted unless the required evidence exists and validates.

## Trust model

The executor's natural-language claim is **not evidence**. Neither is the
model's confidence.

Evidence carries mandatory provenance:

| Source | Meaning | Can satisfy a requirement |
| --- | --- | --- |
| `OBSERVED` | Independently collected from a real signal | Yes, while fresh |
| `EXECUTOR` | Self-reported by the agent doing the work | Never |
| `MODEL` | Generated by an LLM | Never |

The verifier is fail-closed. Every one of these resolves to `ABSTAIN`:

- required evidence missing
- evidence invalid, empty, or tampered
- conflicting evidence for the same requirement
- evidence present but only self-reported
- malformed input
- no declared requirements
- evidence too old for the requirement's freshness horizon
- evidence with no recorded collection time, where freshness is required
- an evidence record that no longer matches its own content hash
- an unexpected exception inside the verifier itself

Critically, **the model cannot tell the verifier that evidence exists.** The
verification tool accepts only `task_id` and `claim`. Requirements and evidence
are read from a runtime-owned ledger that the model has no write path to. An
agent that skips the tool entirely cannot produce a success either — the
orchestrator treats a missing verifier decision as `ABSTAIN`.

## Evidence has a position in time

An observation that cannot be placed in time can be replayed forever, so
evidence records when it was collected, by which collector, and a SHA-256 of
its own content.

Requirements declare their own freshness horizon, because different evidence
ages differently. A health probe speaks only for the moment it ran; a recorded
CI result speaks for as long as the commit it describes.

The most recent trusted observation governs. An older failed probe does not veto
a service that has since been observed healthy — otherwise one transient 503
would make a recovered service permanently unverifiable. A newer failed probe
does veto an earlier success. Observations that are equally recent and disagree
are unresolvable, and abstain.

## The audit trail

Every execution appends immutable events to a journal: the claim, each tool
call, each verification decision, each recovery attempt, and every observation
collected or rejected.

```text
EXECUTION_START      orchestrator  STARTED
AGENT_TURN           executor      RESPONDED
TOOL_CALL            executor      INVOKED       tool=verify_task_completion
VERIFIER_DECISION    verifier      ABSTAIN       missing=['runtime'] failure=EVIDENCE_UNTRUSTED
RECOVERY_START       orchestrator  COLLECTING    missing=['runtime']
EVIDENCE_COLLECTED   collector     HEALTHY       kind=runtime
AGENT_TURN           executor      RESPONDED
TOOL_CALL            executor      INVOKED       tool=verify_task_completion
VERIFIER_DECISION    verifier      VERIFIED
EXECUTION_COMPLETE   orchestrator  VERIFIED
```

Replaying an `execution_id` reconstructs why a task was verified without
trusting any agent's account of it. Events carry correlation ids and a hash of
their own content, and are emitted as single-line JSON with a `severity` field —
the shape Cloud Logging ingests from stdout on Cloud Run, with no client
library and no added dependency.

## Runtime evidence comes from a real probe

Runtime evidence is not a string in a fixture. It is produced by an actual
HTTP request in [`proofos/probe.py`](proofos/probe.py), and the recorded
evidence value is the probe's account of the response it received.

The endpoint must return 2xx with a JSON body containing `{"status": "ok"}`.
Every other outcome fails closed:

| Probe outcome | Evidence recorded | Verifier |
| --- | --- | --- |
| 2xx, `status: "ok"` | `OBSERVED`, valid | `VERIFIED` |
| 5xx / 4xx | `OBSERVED`, invalid | `ABSTAIN` |
| 2xx, body not JSON or off-contract | `OBSERVED`, invalid | `ABSTAIN` |
| 2xx, `status` not `"ok"` | `OBSERVED`, invalid | `ABSTAIN` |
| Redirect | none — refused, not followed | `ABSTAIN` |
| Timeout | none — nothing was observed | `ABSTAIN` |
| Connection failure | none — nothing was observed | `ABSTAIN` |

Redirects are refused rather than followed. Following one would let whoever
controls the health URL point the probe at a machine of their choosing while the
recorded evidence still named the original address — forged provenance.

When no response arrives, no evidence is written at all: a probe that failed to
reach the service has observed nothing, and silence is never proof.

Set `PROOFOS_HEALTH_URL` to probe a real deployment. Left unset, the demo starts
a local health service so the probe still crosses a real socket.

## Google Cloud setup

Create or select a Google Cloud project with billing enabled.

```bash
gcloud auth login
gcloud config set project YOUR_PROJECT_ID
gcloud services enable run.googleapis.com aiplatform.googleapis.com cloudbuild.googleapis.com
```

Create your local environment file:

```bash
cp .env.example .env
```

Set:

```text
GOOGLE_GENAI_USE_VERTEXAI=TRUE
GOOGLE_CLOUD_PROJECT=YOUR_PROJECT_ID
GOOGLE_CLOUD_LOCATION=global
```

`GOOGLE_CLOUD_LOCATION=global` is the Vertex AI endpoint that serves Gemini
3.5 Flash. It is **not** a Cloud Run region — Cloud Run still requires a real
region such as `us-central1` when you deploy.

## Run locally with ADK

Install dependencies:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

On Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Then run the live scenario. This performs a real Gemini call through ADK; the
model must invoke the verification tool to reach any conclusion:

```bash
python -m proofos_agent.run_demo
```

Exit codes: `0` VERIFIED, `1` ABSTAIN, `2` preflight failed (no credentials).

The command prints a structured report containing every tool call the model
made, the verifier's decision on each attempt, and the terminal outcome.

Expected sequence: attempt 1 returns `ABSTAIN` with `missing: ["runtime"]`
because runtime evidence is only self-reported; recovery collects an independent
runtime probe; attempt 2 returns `VERIFIED`.

## Security considerations

- Agent output, tool output, and external content are all treated as untrusted.
- Evidence provenance is mandatory and unforgeable from the model's side: the
  tool schema exposes no parameter through which evidence can be asserted.
- Prompt injection cannot manufacture a `VERIFIED`, because the decision is made
  by deterministic code over ledger contents, not by the model.
- Retries are bounded by an explicit budget; there is no unbounded agent loop.
- No credentials or evidence payloads are committed. `.env` is gitignored.

## Known limitations

- The evidence ledger and journal are in-memory. The journal is written behind
  a sink interface with an in-memory implementation; a Firestore sink is the
  next step and is **not built**, so decisions are not durable across processes.
- Evidence hashing detects silent mutation of stored records. It is not a
  signature and does not prove who wrote a record.
- The runtime collector performs a real HTTP probe, but the demo target is a
  local health service unless `PROOFOS_HEALTH_URL` points at a deployment.
- Only one evidence kind is collected live. Test evidence is still a recorded
  CI result rather than a freshly executed suite.
- Cloud Run deployment is documented but not yet proven end to end.
- Observability (Cloud Logging / OpenTelemetry traces) is not yet instrumented.
